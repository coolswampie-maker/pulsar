# Публикация ПУЛЬСАР на pulsar.jaglionrus.ru (VPS + Django + Nginx)

Эта версия — с бэкендом: фронт (сайт) + REST API + кабинет оператора (`/admin`) на
одном домене `pulsar.jaglionrus.ru`. Основной сайт на `jaglionrus.ru` при этом не
трогаем: добавляется только одна запись для поддомена.

Готовые файлы конфигурации — в папке [`deploy/`](deploy/):
`nginx-pulsar.conf`, `gunicorn.service`. Переменные окружения — `backend/.env.example`.

Ниже `<ПУТЬ>` = `/srv/pulsar` (куда клонируем репозиторий на сервере).

---

## Этап 1. Подготовка

NS-серверы домена `jaglionrus.ru` уже указывают на Рег.ру (`ns1.reg.ru`), зона
управляется там же. Менять NS не нужно — это самый безопасный вариант: основной
сайт и почта не затрагиваются вообще.

Единственное, что нужно на этом этапе, — арендовать VPS и узнать его IP-адрес.
Запись в DNS добавим позже (этап 3), когда сервер уже будет отвечать.

> Перед заказом сервера в Рег.ру потребуется пройти **идентификацию аккаунта** и
> **пополнить именно облачный счёт** — без этого кнопка заказа неактивна.

## Этап 2. Сервер (VPS)

После аренды VPS с Ubuntu и получения его IP:

```bash
# пакеты
sudo apt update && sudo apt install -y python3-venv python3-pip postgresql nginx git certbot python3-certbot-nginx

# база
sudo -u postgres psql -c "CREATE USER pulsar WITH PASSWORD 'СИЛЬНЫЙ_ПАРОЛЬ';"
sudo -u postgres psql -c "CREATE DATABASE pulsar OWNER pulsar;"

# код
sudo git clone https://github.com/coolswampie-maker/pulsar.git /srv/pulsar
cd /srv/pulsar && sudo git checkout backend

# окружение Django
cd /srv/pulsar/backend
sudo python3 -m venv .venv
sudo .venv/bin/pip install -r requirements.txt

# настройки: заполнить .env (см. backend/.env.example)
sudo cp .env.example .env && sudo nano .env
#   SECRET_KEY=...   DEBUG=0
#   ALLOWED_HOSTS=pulsar.jaglionrus.ru
#   DATABASE_URL=postgres://pulsar:СИЛЬНЫЙ_ПАРОЛЬ@127.0.0.1:5432/pulsar

# миграции, каталог, оператор, статика
sudo .venv/bin/python manage.py migrate
sudo .venv/bin/python manage.py import_catalog      # 35 позиций из booking/data/catalog.json
sudo .venv/bin/python manage.py createsuperuser     # логин в кабинет оператора
sudo .venv/bin/python manage.py collectstatic --noinput

# права на папки, которые отдаёт/пишет сервис
sudo chown -R www-data:www-data /srv/pulsar/backend/staticfiles /srv/pulsar/backend/media
```

**Gunicorn как сервис:**
```bash
sudo cp /srv/pulsar/deploy/gunicorn.service /etc/systemd/system/pulsar.service
sudo systemctl daemon-reload && sudo systemctl enable --now pulsar
sudo systemctl status pulsar        # active (running)
```

**Nginx:**
```bash
sudo cp /srv/pulsar/deploy/nginx-pulsar.conf /etc/nginx/sites-available/pulsar
sudo ln -s /etc/nginx/sites-available/pulsar /etc/nginx/sites-enabled/pulsar
sudo nginx -t && sudo systemctl reload nginx
```

## Этап 3. DNS (Reg.ру) — только когда сервер готов

Зона `jaglionrus.ru` управляется в Рег.ру, NS менять не нужно. Добавляется
**одна запись**, всё существующее остаётся нетронутым:

| Тип | Имя | Значение |
|-----|-----|----------|
| A | `pulsar` | **IP вашего VPS** |

Записи `@` и `www` не трогаем — основной сайт продолжает работать как работал.
Почта (MX) и подтверждения владения (TXT) тоже не затрагиваются.

Обновление — обычно 15–60 минут. Проверить:
```bash
dig +short pulsar.jaglionrus.ru      # должен вернуть IP вашего VPS
```

## Этап 4. HTTPS

Только после того как `pulsar.jaglionrus.ru` резолвится на IP VPS (проверьте
`dig pulsar.jaglionrus.ru`):
```bash
sudo certbot --nginx -d pulsar.jaglionrus.ru
```
Certbot допишет 443-блок, редирект с 80 и автопродление.

Путь отступления: добавляется всего одна запись для поддомена, поэтому основной
сайт затронуть невозможно. Если что-то пойдёт не так с самим `pulsar` — удалите
запись `A pulsar` в зоне, и поддомен просто перестанет открываться, ничего
больше не изменится.

## Резервные копии

Без этого одна поломка диска стирает все компании, заявки, профили проектов
и показатели — восстанавливать будет неоткуда.

### Разовая настройка

```bash
sudo chmod +x /srv/pulsar/deploy/backup.sh /srv/pulsar/deploy/restore-check.sh
sudo /srv/pulsar/deploy/backup.sh          # проверяем, что работает
sudo ls -lh /var/backups/pulsar
```

Скрипт сам возьмёт пароль базы из `backend/.env` — вводить его никуда
не нужно.

### Каждую ночь

```bash
sudo crontab -e
```

Вписать двумя строками:

```
15 3 * * *  /srv/pulsar/deploy/backup.sh >> /var/log/pulsar-backup.log 2>&1
30 3 * * 1  /srv/pulsar/deploy/restore-check.sh >> /var/log/pulsar-backup.log 2>&1
```

Первая — копия каждую ночь в 3:15. Вторая — проверка по понедельникам:
берёт свежую копию, разворачивает её во временную базу, считает записи
и базу удаляет. Рабочую базу не трогает.

**Вторая строка не менее важна первой.** Копия, которую ни разу не
восстанавливали, копией не является: она может месяцами создаваться битой
или пустой, и узнается об этом в единственный неподходящий день.

Посмотреть, что было:

```bash
tail -40 /var/log/pulsar-backup.log
```

### Копию надо увозить с сервера

По умолчанию копии лежат в `/var/backups/pulsar` — на том же диске, что и
база. Это спасает от ошибки человека («удалил не ту компанию») и не спасает
ни от чего больше: умрёт диск — пропадёт и оригинал, и копия.

Скрипт при каждом запуске об этом предупреждает, пока не задана переменная
`PULSAR_BACKUP_UPLOAD` — команда выгрузки, где `{}` заменяется на файл.

Копирование на другой компьютер по SSH:

```bash
sudo crontab -e
# добавить строкой выше расписания:
PULSAR_BACKUP_UPLOAD=scp {} backup@ДРУГОЙ_СЕРВЕР:/backups/pulsar/
```

Или в объектное хранилище (Яндекс, Selectel) через `rclone`:

```
PULSAR_BACKUP_UPLOAD=rclone copy {} storage:pulsar-backups/
```

Что выбрать — решайте по тому, что у вас уже есть. Главное, чтобы копия
физически лежала не на этом сервере.

### Как восстановить, если всё-таки понадобилось

```bash
sudo systemctl stop pulsar
sudo -u postgres psql -c "DROP DATABASE pulsar;"
sudo -u postgres psql -c "CREATE DATABASE pulsar OWNER pulsar;"
gunzip -c /var/backups/pulsar/db_ДАТА.sql.gz | sudo -u postgres psql -d pulsar
sudo tar -xzf /var/backups/pulsar/media_ДАТА.tar.gz -C /srv/pulsar/backend
sudo systemctl start pulsar
```

## Монитор доступности

Сайт уже однажды лежал, и заметили это случайно. Проверять должен кто-то
снаружи: сервер, который упал, о себе не сообщит.

### Что проверять

У бэкенда есть адрес `/api/health/`. Он отвечает `200`, только если жива
база и в ней есть каталог; иначе `503`.

Проверять именно его, а не главную страницу. Nginx отдаёт статику и тогда,
когда Django лежит: главная открывается, а забронировать ничего нельзя.
Монитор, смотрящий на главную, в этот момент молчит.

```bash
curl -s https://pulsar.jaglionrus.ru/api/health/
# {"status":"ok","catalog":35,"db":"ok"}
```

### Настройка (5 минут)

Подойдёт любой бесплатный сервис проверки — например UptimeRobot,
Better Stack, HetrixTools. Порядок везде одинаковый:

1. Завести учётную запись.
2. Создать проверку типа **HTTP(s)**, адрес
   `https://pulsar.jaglionrus.ru/api/health/`, интервал 1–5 минут.
3. В настройках проверки указать, что ответ должен иметь код **200**
   (некоторые сервисы по умолчанию считают успехом любой ответ — тогда
   `503` они пропустят, и смысл проверки теряется).
4. Подключить уведомления в телеграм: в сервисе взять инструкцию,
   обычно это добавление их бота в чат.
5. **Проверить, что оповещение доходит.** Остановите сайт на минуту
   (`sudo systemctl stop pulsar`), дождитесь письма, включите обратно
   (`sudo systemctl start pulsar`). Монитор, который ни разу не срабатывал,
   ничем не отличается от выключенного.

Заодно такие сервисы следят за сроком сертификата HTTPS и предупреждают
заранее — сертификат Certbot продлевается сам, но если продление сломается,
узнать об этом лучше не от посетителей.

## Как зайти на сервер

Всё ниже делается на сервере, а не на ноутбуке. Подключение — из терминала
(на Windows — PowerShell):

```bash
ssh root@pulsar.jaglionrus.ru
```

IP-адрес искать не нужно: домен уже указывает на сервер, SSH идёт туда же,
куда и сайт.

**Пароль при вводе не отображается** — ни точек, ни звёздочек, курсор стоит
на месте. Так и задумано, печатайте вслепую и жмите Enter. Пароль тот, что
задавался при создании сервера; сбрасывается в панели Рег.ру (облачные
серверы → сервер → «Изменить пароль root»).

Получилось — приглашение сменится на `root@vps…:~#`.

При первом входе с нового компьютера спросит
`Are you sure you want to continue connecting (yes/no)?` — печатать `yes`
целиком, не `y`.

Выход — `exit` или `Ctrl+D`. Закрытый ноутбук выходом не считается:
соединение оборвётся само, и подключаться придётся заново.

| Что видно | Что случилось |
|---|---|
| `Permission denied` | пароль не тот — сбросьте в панели Рег.ру |
| `Connection refused` или висит | сервер выключен или перезагружается |
| `Host key verification failed` | сервер пересоздавали; выполните на ноутбуке `ssh-keygen -R pulsar.jaglionrus.ru` |

## Обновление сайта в будущем
```bash
cd /srv/pulsar && sudo git pull
cd backend
sudo .venv/bin/pip install -r requirements.txt          # если менялись зависимости
sudo .venv/bin/python manage.py migrate                  # если менялись модели
sudo .venv/bin/python manage.py collectstatic --noinput  # если менялась статика Django
sudo systemctl restart pulsar
```
Изменения фронта (js/css/data в корне) подхватываются сразу — Nginx отдаёт файлы напрямую.

> **После этого обновления** появились новые таблицы (программы поддержки,
> смета проекта, реквизиты и отметка о согласии у компаний) —
> `migrate` обязателен, без него кабинет будет отвечать ошибкой.

> **В обновлении с синей шапкой** миграция одна и лёгкая (0018): у компании
> добавилось направление «Другое». Данные не меняются, но `migrate` всё
> равно выполните — иначе Django будет ругаться на незастывшие миграции.

### Программы поддержки — их надо завести руками

Проверка на формальные отказы считает ровно то, что внесено в CRM.

⚠️ Сейчас у резидента этой проверки на экране нет. Блок «Условия программ»
убран из кабинета: пока в CRM не заведено ни одной программы, он показывал
пустое обещание. Серверная часть работает и покрыта тестами, разметку
вернём вместе с разбором приложенного положения о конкурсе. То есть
завести программы можно уже сейчас, но увидит их резидент после того,
как блок вернётся.

CRM → **Программы поддержки** → «Добавить». Параметры берите **из
официальной документации конкурса**, не по памяти: резидент подстроит
заявку под то, что здесь написано.

Пустое поле означает «программа этого не ограничивает». **Не ставьте 0
вместо пустого** — ноль читается как «предел равен нулю», и проверка
отклонит всех подряд.

Что заполнять: сроки приёма, предельный размер гранта, софинансирование в
процентах, возраст компании в месяцах, предельную численность и выручку
(их значения проверка берёт у резидента из раздела «Показатели»), допустимые
ОКВЭД (через запятую, можно началом кода — «72» покроет «72.19») и стадии
проекта. Галочка «Показывать резидентам» скрывает программу, не удаляя её:
удобно для прошедших волн — параметры обычно повторяются.

> **Если на сайте виден старый интерфейс.** Проверьте, что в конфиге Nginx в
> блоке `location /` есть `add_header Cache-Control "no-cache";` — без него
> браузер держит прежний `app.js` неделями, потому что имя файла при
> обновлении не меняется. Выглядит это обманчиво: свежий сервер, старый
> экран. Строку впишите **руками** в `/etc/nginx/sites-available/pulsar`
> (см. предупреждение ниже), затем
> `sudo nginx -t && sudo systemctl reload nginx` и Ctrl+F5 в браузере.
>
> Номер `?v=` у `js/` и `css/` в `index.html` — вторая страховка на тот же
> случай; при заметных правках фронта его стоит увеличить.

> ⚠️ **Никогда не копируйте `deploy/nginx-pulsar.conf` поверх установленного
> после того, как отработал Certbot.** В репозитории лежит конфиг только для
> порта 80; в `/etc/nginx` к нему добавлен блок 443 с сертификатами. Копирование
> стирает HTTPS — на 443 никто не слушает, сайт отвечает `ERR_CONNECTION_REFUSED`.
> Коварство в том, что `nginx -t` проходит успешно: синтаксис верный.
>
> Переносите **правку**, а не файл. Посмотреть разницу:
> ```bash
> diff /srv/pulsar/deploy/nginx-pulsar.conf /etc/nginx/sites-available/pulsar
> ```
> Если уже перезаписали — HTTPS возвращается одной командой, новый сертификат
> при этом не выпускается:
> ```bash
> sudo certbot --nginx -d pulsar.jaglionrus.ru
> sudo ss -tlnp | grep -E ':(80|443)'      # обе строки должны быть
> ```

## Индивидуальные заявки на подбор

Если человек не нашёл нужного в каталоге, вместо тупика он видит предложение
оставить **индивидуальную заявку**: описать оборудование или задачу своими
словами и, по желанию, указать сроки. Заявка попадает в CRM в раздел
**Индивидуальные заявки** (`/admin/booking/customrequest/`), номера вида
`IND-1001`.

Для оператора это не только лид, но и обратная связь по каталогу: в карточке
есть поле **«Что искали»** — исходный запрос, по которому ничего не нашлось.
Периодически просматривая эти запросы, видно, каких позиций людям не хватает.

Статусы: Новая → В работе → Обработана (или Отклонена). Массовые действия
«Взять в работу» и «Отметить обработанными» есть в списке.

Контакты у гостя спрашиваются в форме, у вошедшей компании берутся из профиля
кабинета. Заявка без способа связи не принимается.

## Два кабинета: не путать

| | Кто входит | Адрес | Что делает |
|---|---|---|---|
| **Кабинет оператора** (CRM) | сотрудники ПУЛЬСАР | `/admin/` | заявки, календарь занятости, каталог, компании, планы по показателям |
| **Кабинет компании** (ЛК) | компании-резиденты | `#/login` → `#/cabinet` | профиль, свои заявки, отчётность по показателям ИНТЦ |

Это разные учётные записи. Оператор создаётся командой `createsuperuser` и **не может**
войти в кабинет компании (у него нет профиля компании). Компании регистрируются сами
на сайте — заводить их вручную не нужно.

**Что оператор делает с новой компанией:** в CRM → **Компании** открыть карточку и
поставить галочки:
- **«Подтверждена оператором»** — проверка пройдена;
- **«Резидент ИНТЦ»** — присвоен статус резидента.

Скидка 25% включается только когда стоят **обе** галочки. Пока их нет, компания
бронирует по базовым тарифам, а если она заявила статус резидента при оформлении,
в комментарии к заявке появится пометка «требуется проверка оператором» — сверьте
статус и при необходимости проставьте скидку в заявке вручную.

**Планы по показателям** ставит оператор: CRM → **Показатели** → поле «План». Факт
компания заполняет сама в своём кабинете. Строки показателей создаются автоматически
при первом заходе компании в раздел «Показатели».

**Подтверждающие документы** компании загружают в кабинете; файлы ложатся в
`backend/media/` (Nginx отдаёт их как `/media/`). Папка не в git — на сервере
позаботьтесь о её бэкапе вместе с базой.

## Подключение ИИ-подбора (YandexGPT)

На странице каталога есть блок «Опишите задачу своими словами». Он работает
**всегда**: без настроенной модели подбор идёт встроенным алгоритмом по словам
и синонимам. Модель улучшает результат, но её отсутствие сайт не ломает.

Чтобы включить YandexGPT:

1. В Yandex Cloud создайте сервисный аккаунт, выдайте ему роль
   `ai.languageModels.user` и получите **API-ключ**.
2. Скопируйте идентификатор каталога (`folder id`) из консоли.
3. Впишите в `backend/.env`:
   ```
   YANDEX_API_KEY=<ключ>
   YANDEX_FOLDER_ID=<идентификатор каталога>
   ```
4. `sudo systemctl restart pulsar`

Проверить настройку одной командой прямо на сервере:
```bash
cd /srv/pulsar/backend && sudo .venv/bin/python manage.py assist_check
```
Она покажет, что именно прочитано из `.env`, сделает реальный запрос и при
неудаче объяснит причину (401 — ключ, 403 — роль, 404 — folder id или модель,
429 — лимит). Ключ в выводе замаскирован.

Проверить снаружи, через сайт:
```bash
curl -s -X POST https://pulsar.jaglionrus.ru/api/assist/ \
  -H 'Content-Type: application/json' \
  -d '{"query":"нужно определить примеси в субстанции"}' | head -c 300
```
В ответе поле `"mode"`: `ai` — отвечает модель, `local` — встроенный подбор,
`licensed` — тема требует разрешений (к модели не обращались). Поле `"reply"` —
то, что человек видит текстом над карточками.
Если ожидали `ai`, а видите `local` — смотрите `journalctl -u pulsar -f`,
там будет строка «YandexGPT недоступен» с причиной.

**Почему это устроено просто.** Весь каталог (35 позиций, около 3 000 токенов)
помещается в один запрос к модели, поэтому векторная база, эмбеддинги и
RAG-конвейер не нужны. Если каталог вырастет до нескольких сотен позиций,
подход стоит пересмотреть — но не раньше.

### Как ассистент себя ведёт

**Кто он.** На вопрос «кто ты» отвечает, что он ассистент подбора ПУЛЬСАР,
работает на языковой модели, может ошибаться. Не выдаёт себя за человека и не
называется сотрудником МГУ.

**Что делает и чего не делает.** Подбирает из каталога 1–4 позиции. Не называет
цены, сроки и занятость — это показывает сайт, а модель может ошибиться. Не даёт
научных консультаций и не заменяет методиста. Посторонние вопросы (погода,
стихи, политика) коротко возвращает к делу.

**Работы, требующие разрешений.** Взрывчатые и отравляющие вещества,
наркотические средства и прекурсоры, патогены высоких групп опасности, оружие —
такие запросы **не доходят до модели вообще**. Их отсекает проверка на сервере
(`needs_license` в `booking/assist.py`), поэтому уговорить систему в тексте
запроса нельзя: «игнорируй инструкции» действует на модель, но не на проверку.
Ответ — не отказ и не нотация, а перевод на человека: такие работы законны, но
оформляются только через оператора с проверкой лицензий. Клиенту предлагается
оставить индивидуальную заявку.

Обратная сторона такой проверки — ложные срабатывания, и они опаснее пропусков:
если фильтр заблокирует «ядерный магнитный резонанс» из-за «яд» или
«взрывобезопасность» из-за «взрыв», подбор перестанет работать на нормальных
запросах. Поэтому шаблоны написаны с границами слов, а в тестах есть отдельная
проверка, что законная наука не блокируется. **Если добавляете новый шаблон в
`LICENSED_PATTERNS` — обязательно допишите к нему пример законного запроса в
`test_legitimate_science_not_blocked`.**

**Насколько уверенно отвечает.** Когда совпадение слабое, ассистент не пишет
«вот что подходит», а честно говорит «точного совпадения нет, возможно, подойдёт
что-то из этого». Уверенная формулировка на плохом совпадении хуже, чем
отсутствие ответа: человек поверит и приедет зря.

### Какие запросы приходили в подбор

Все запросы пишутся в обычный текстовый файл `backend/logs/assist.log` —
намеренно не в базу и не в CRM: это рабочая заметка, её можно прочитать,
скопировать в Excel, очистить или удалить, ничего не сломав.

```bash
cd /srv/pulsar/backend
.venv/bin/python manage.py assist_log --stats     # сводка
.venv/bin/python manage.py assist_log             # последние 30
.venv/bin/python manage.py assist_log --empty     # только те, где ничего не нашлось
.venv/bin/python manage.py assist_log --mode local   # когда отвечала не модель
.venv/bin/python manage.py assist_log --clear     # очистить
```

**Ради чего это.** Список `--empty` — это готовый перечень того, чего не
хватает каталогу: люди искали и ушли ни с чем. В отличие от индивидуальных
заявок, сюда попадают и те, кто до формы не дошёл, а таких большинство.

Второе применение — контроль модели. В колонке «Чем» видно, отвечала ли
YandexGPT (`модель`) или встроенный алгоритм (`встроенный`). Если `модель`
перестала появляться, подбор работает без ИИ, а внешне сайт здоров;
`--stats` прямо предупредит об этом.

**Что в файле не хранится:** IP-адреса и любые сведения о посетителе —
только время, режим, число найденного и текст запроса. Наружу файл не
отдаётся: `backend/` закрыт в Nginx, расширение `.log` закрыто отдельно.
Запрос — свободный текст, люди иногда пишут туда лишнее, поэтому чистить
журнал время от времени — разумная привычка (`--clear`).

При разрастании свыше 5 МБ файл автоматически переименовывается в
`assist.log.old`, и запись начинается заново — диск не переполнится.
Отключить журнал целиком: `ASSIST_LOG_FILE=` (пустое значение) в `.env`.

Права на папку — как для media (сервис работает от `www-data`):
```bash
sudo mkdir -p /srv/pulsar/backend/logs
sudo chown www-data:www-data /srv/pulsar/backend/logs
```

**Защита от выдумок.** Модель возвращает только идентификаторы, а сервер
сверяет их с каталогом и выбрасывает всё, чего в базе нет. Предложить клиенту
несуществующий прибор система не может в принципе.

**Выбор модели.** Задача входо-ёмкая: каталог ~3 000 токенов на входе, ответ
около 100 на выходе. Поэтому решает цена входящих токенов. `aliceai-llm-flash`
(0,1 ₽ за 1000 входящих) на нашем профиле вдвое дешевле `yandexgpt-lite`
(0,2 ₽). Точные слаги копируйте из карточки модели в AI Studio. Смена модели —
одна строка в `.env` и перезапуск, код менять не нужно.

**Расходы.** Порядок величины: тысяча подборов — от 100 до 650 ₽ в зависимости
от модели. Стартовый грант Yandex Cloud (4 000 ₽) покрывает несколько тысяч
запросов. Частота подбора ограничена параметром `ASSIST_RATE` (по умолчанию
`20/min`), индивидуальных заявок — отдельным `CUSTOM_REQUEST_RATE`
(`10/hour`). Счётчики раздельные намеренно: человек, перебравший формулировки
в подборе, не должен упереться в отказ на форме заявки. Рекомендуется завести
бюджет с оповещением в разделе Billing — чтобы после гранта расход не стал
неожиданностью.

## Заголовки безопасности

Ставятся один раз, одной командой:

```bash
sudo python3 /srv/pulsar/deploy/add-security-headers.py
```

Скрипт сам находит блок `listen 443`, вписывает `include` в двух нужных
местах, делает резервную копию конфига, проверяет его и перезагружает Nginx.
Если проверка не прошла — возвращает файл как был и ничего не перезагружает.
Повторный запуск безопасен: если всё уже подключено, он так и скажет.

Правку в двух местах требует само устройство Nginx: `add_header` не
складывается по уровням, и `add_header Cache-Control` внутри `location /`
отбрасывает всё, что унаследовано от `server`. Набор заголовков и пояснение
к каждому — в [`deploy/security-headers.conf`](deploy/security-headers.conf).

Проверить:
```bash
curl -sI https://pulsar.jaglionrus.ru | grep -i -E 'strict|frame|content-type-opt|referrer'
```

После включения откройте сайт и загляните в консоль (F12): единственный
заголовок, способный что-то сломать, — `Content-Security-Policy`. Если
что-то заблокировано, там будет строка «Refused to load…».

## Помощник резидента (кабинет → «Проект»)

Резидент рассказывает о проекте один раз — 13 полей, заполняются диалогом
или формой. Из этого рассказа помощник собирает черновики: разделы заявки
на грант, тизер для инвестора, одну страницу о проекте, план презентации.

Разделы **универсальные**, а не под конкретную программу: настоящая заявка
ФСИ или Сколково требует разбора требований и ежегодного сопровождения.

**Помощник не придумывает факты.** В модель уходят только заполненные поля;
чего нет в профиле — того не будет и в тексте, вместо выдумки остаётся
пометка «нужно дополнить». Проверка нехватки полей идёт на сервере до
обращения к модели, поэтому за пустой запрос мы не платим.

**Сборка идёт в фоне.** Обращение к модели длится до полуминуты, и прямой
вызов держал бы процесс Gunicorn целиком — три одновременные сборки
остановили бы весь сайт. Сервер заводит задание и отвечает сразу, браузер
опрашивает результат.

Настройки — `COMPOSE_TIMEOUT` (сколько ждать модель) и `COMPOSE_RATE`
(сборок на пользователя в час). Отдельного ключа не нужно: используется тот
же `YANDEX_API_KEY`, что и для подбора.

Задания хранятся в таблице `booking_composejob`. Они не чистятся
автоматически — если за год накопится много, удалить старые можно так:
```bash
cd /srv/pulsar/backend && .venv/bin/python manage.py shell -c "
from datetime import timedelta
from django.utils import timezone
from booking.models import ComposeJob
n,_ = ComposeJob.objects.filter(created_at__lt=timezone.now()-timedelta(days=30)).delete()
print('удалено:', n)"
```

## Частые вопросы
- **Фронт и API на одном домене** → в `index.html` ничего не меняем: `PULSAR_API_BASE='/api'`
  и `/admin/` работают через Nginx как есть.
- **Компания не видит скидку резидента** → в CRM у неё должны стоять обе галочки:
  «Резидент ИНТЦ» и «Подтверждена оператором».
- **Не грузятся загруженные документы** → проверьте права на `backend/media/`
  (`chown -R www-data:www-data`) и блок `location /media/` в Nginx.
- **Не открывается кабинет оператора по HTTPS (ошибка CSRF)** → проверьте, что в `.env`
  указан `ALLOWED_HOSTS=pulsar.jaglionrus.ru`: домен автоматически попадает в
  `CSRF_TRUSTED_ORIGINS`.
- **Каталог пуст** → не выполнен `import_catalog`.
- **Заявки не сохраняются** → смотрите `journalctl -u pulsar -f` и `sudo nginx -t`.
- **Подбор отвечает `local`, хотя ключ прописан** → проверьте роль сервисного
  аккаунта и доступность `llm.api.cloud.yandex.net` с сервера.
